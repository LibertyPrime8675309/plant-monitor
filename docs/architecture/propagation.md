# Propagation (prototype)

Part of the notes on how Plant record is built. The short map is `docs/ARCHITECTURE.md`; this file holds the detail for one prototype.

## Propagation (prototype, proto/propagation)
- `plantdb/propagation.py` (ORDER 63). Tables are made by `prop_db()` the first time any of its routes runs (`PROP_SCHEMA`, once per database file), so `core.py` and `init_db()` are untouched and no column is added to `plants`: `propagations` (code PR-001..., method, parent_code, species, count, started_on, medium/setup/hormone/place, check_every, status active|ready|done|failed|gave_away), `prop_events` (kind check, water, callus, roots, shoot, union, sprouted, lost, note; `n` for the counted ones), `prop_stages` (an ordered treatment plan: kind, days, temperatures, started_on, ended_on) and `prop_children` (which plants a piece became; `plant_code` is unique).
- `METHODS` has the twelve ways with their guide section, the usual days between looks and which events make sense. `prop_card()` is the one answer for an attempt: events, stages with state and days left, children, counts, `needs` (a stage ending within `SOON_DAYS`, the next stage waiting, a look due) and `due`. `check_days()` is the person's number, else 7 for water or seed, else the way's usual.
- `prop_make_plant()` repeats the steps of `plants.create_plant()` (next P-code, first version, audit row) and `POST /api/propagations/<id>/promote` copies `PLANT_FACT_FIELDS` plus a few identity fields from the parent, never its spot, pot, container, photos or pests found. Lost pieces count against the room left. Family and results are computed from these tables on every request (`/api/propagations/tree`, `/plant/<code>`, `/results`); nothing is cached or stored twice.
- **Names are shared.** Every module's top-level names are linked into every other, so this file's helpers start with `prop_` (`iso` and `plant_photo` clashed with other modules and broke backups until renamed; `dev/test/unit/test_lint.py` does not see this kind of clash).
- Front end `js/propagation.js` (every name starts `prp`), `css/propagation.css`. `addFeature()`: the page `#/propagating` (also `/new`, `/family`, `/<id>`; no `section`, so no top-bar link), a Today block `today-prop` (order 66), plant-page add `prp-plant` after `#uses`, and `prp-guidelink` on the guide. Tables use `.tbl-wrap > table.tbl` so `fitTables()` stacks them; the app's form handler passes only the form, so a form that needs to say which button was pressed uses a hidden input.
- **Seed lots and photos (November 15, 2026).** `prop_events` has `n2` and `how` (added by `prop_db()` to a record an earlier build made): a seed test is `{kind: 'test', how: float | cut, tested, sound, discard?}`, stored as `n` sound of `n2` tried; with `discard` a second event `lost` takes the failed ones off the lot. `sown` is a counted event (never more than the lot holds). The card gives `sown`, `tests`, `last_test`, `sprout_of` (the seeds sown, else the lot) and `sprout_pct`. `sown` and `test` are refused for anything but a seed lot (`SEED_ONLY`). Photos: table `prop_photos`, `POST /api/propagations/<id>/photos` (form field `files`, `caption`; `save_image()` as for a plant), `DELETE /api/propagations/photos/<id>` (the file goes to `photos_deleted`). They are not yet in the offline photo list or the JSON download.
- **Home limits.** `prop_row()` calls `home_check()` with the parent plant's code, so every route that changes an attempt is refused for an editor limited to other homes; `prop_make_plant()` calls `home_check_new()` with the home the new plant gets (the parent's, else the main one). `test_home_limit.py` tries each route.
- Tests: `dev/test/unit/test_propagation.py`; `dev/test/propagation_check.py` (the whole flow through the API and the page, phone width, dark mode with large text, the largest text, a seed lot's test, sowing and photos, spoken names and contrast, view-only).
- **Notification (November 15, 2026).** `prop_push(c, at=None)` is in core's `PUSH_CLOCK` and the kind `prop` in `PUSH_EXTRA_KINDS` (the same two lists `proto/reminders` uses; the lines in `core.py` and `push.py` are identical in both branches). Once a day, by the main home's clock, when any active attempt has something due (`push_once` key `prop:<day>`); it does nothing until the `propagations` table exists.
- **Library facts for seed (November 15, 2026).** `FACT_FIELDS` has `about_seed` (json: `{text, steps: [{kind, days, days_low, days_high, temp_low, temp_high}], keep}`; the species page shows `text`). `app/seed/batches/batchD2.json` adds eleven accepted facts with `source_kind: reference`, each source written `Title | https://...` (two sources joined by ` ; `); a fact marked `likely` has a `note` saying why. `seed_fact(c, name, parent)` in `propagation.py` reads the accepted fact through `facts_of()` and `GET /api/propagations/seedfacts?name=|parent=` returns it. The Start page (`prpSeedLook()`, change handler `prpseed` on the way, the parent and the species; `after` on the view) shows it in `#prp-seedfacts`, and `prpseeduse` fills the step boxes. **Batch name D2 is taken by this branch.** The Start page draws once more shortly after it opens, which empties a box typed into at once; the check types again until it holds.
