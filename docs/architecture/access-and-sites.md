# Remote access, how the container starts, homes and sites

Part of the notes on how Plant record is built. The short map is `docs/ARCHITECTURE.md`; this file holds the detail for one area, moved here word for word on November 15, 2026.

## Notes from the back end and front end lists
- **1.12.0 additions (remote access):**
  - **Ports:** gunicorn listens on three ports in the container.
    - 8080 is "this computer". It is published on 127.0.0.1 only (`PLANTDB_BIND` in `.env` opens it). It has full access, with the optional `PLANTDB_PASSWORD`.
    - 8081 (`TS_PORT`) is reached only by the `tailscale` container. It is never published.
    - 8082 (`SENSOR_PORT`) accepts only `POST /api/readings`. It is published on 127.0.0.1 unless `PLANTDB_SENSOR_BIND` opens it.
    - `via_tailscale()` compares `SERVER_PORT` (the real listener, not the Host header).
  - **Identity:** Tailscale Serve (`tailscale/config/serve.json`: HTTPS on 443, proxy to `http://plants:8081`, Funnel off) adds `Tailscale-User-Login`/`-Name` and strips spoofed copies. `ts_user()` keeps the table `people(login, name, role, first_seen, last_seen)`. The first person is the owner (or the one the setup script sets); the rest start as `viewer`. Requests on 8081 with no login are refused.
  - **This computer's port answers only to names a stranger cannot point at it (1.58.0):** on 8080 every request is the owner's, and nothing checked the `Host` header, so a page whose name was re-pointed at 127.0.0.1 (DNS rebinding) was the same site to the browser, `X-Editor` and the Origin check included. `host_known()` in core, called in `guard()`'s local branch before the password: number addresses, `localhost`, single-label names, `LOCAL_SUFFIXES` (home-network endings, and `.test` and `.localhost`, which are reserved so nobody can own a name there; `copy_check.py` opens the app as `plants.test`), `PLANTDB_HOSTS` (commas, `.env`; `EXTRA_HOSTS`), and the hosts of `base_url` and the calendar's `public_base`; anything else gets a plain 403 that names `PLANTDB_HOSTS`. `/healthz`, the sensor port, `public_link()` paths and the Tailscale port are answered before it. Tests: `dev/test/unit/test_safety_1580.py`.
  - **From the internet (1.58.0):** Funnel on the PC's own Tailscale publishes `/cal` and `/share` of port 8080 (the README's commands), the port where every other request is the owner's. Tailscale sets `Tailscale-Funnel-Request: ?1` on each request that came in through Funnel and deletes any copy the visitor sent (`addTailscaleIdentityHeaders` in its `ipn/ipnlocal/serve.go`); it also forwards a request for the mount point itself (`/share`) to the same path. So `guard()` starts with `from_funnel() and not public_link()` → a plain 404, before the newer-database page, the password and everything else. `public_link()` is the one list of what needs no person: `GET/HEAD /cal/...` and `GET/HEAD/POST /share/<token of 20+>...`; the routes there check their own tokens. **A new public route must be added to `public_link()`**; `test_every_address_the_app_has_is_closed_to_the_internet` walks the route table as a visitor and fails otherwise. The phone share-sheet target moved from `/share` to `/share-in` (`SHARE_IN` in review.py, the manifest's `share_target.action`; `sw.js` answers both, for an installed app whose manifest is still the old one), so nothing under the published prefix takes pictures; `/share` itself is a redirect to `#/share`. Until 1.58.0 `POST /share` took pictures from anyone who reached it through Funnel, with only an `X-Editor` header.
  - **Roles:** `role_refusal()` enforces them in `guard()`.
    - Viewers can't make changes.
    - `/api/backups*`, `/api/ingest*` and `/api/people` are owner only, as are changes to `/api/settings`, `/api/weather/settings` and `/api/places/<id>`.
    - `editor()` returns the Tailscale name for Tailscale requests.
    - Routes: `GET/PUT /api/me`, `GET/PUT/DELETE /api/people`. `/api/meta` includes `me`. HSTS is sent on 8081.
  - **Container:** user 10001, `read_only`, tmpfs `/tmp`, `cap_drop: ALL`, `no-new-privileges`. `_check_writable()` prints `PLANTDB_NOT_WRITABLE` if the data folders can't be written. The updater then writes `docker-compose.override.yml` (user root plus the file capabilities it needs) and restarts.
  - **Updater:** runs `docker compose build --pull`, then `pull --ignore-buildable` (the tailscale image), then `up -d`.
- **1.12.1 additions (starting the container):**
  - **Which user:** the container starts as root and runs `app/start.py`.
    - A brand-new, empty `data` or `backups` folder is chowned to 10001; nothing else is changed.
    - A forked child switches to 10001 (`setgroups([])`, `setgid(0)`, `setuid(10001)`) and runs `writable.problem()`: every data folder takes a test file, and the database and its SQLite side files open read-write.
    - If that passes, the process switches to 10001 and execs gunicorn with no capabilities left. If not, it stays root (logged as `PLANTDB_RUNNING_AS_ROOT: …`).
    - `PLANTDB_RUN_AS=root` skips the check. `PLANTDB_RUNS_AS` passes the result to the app, and `/api/meta.runs_as` shows it to owners (Debug window).
    - Compose grants SETUID and SETGID (to switch), plus CHOWN, DAC_OVERRIDE and FOWNER (for the root case), on top of `cap_drop: ALL`.
  - `_check_writable()` in server.py uses the same `writable.problem()`. `PLANTDB_NOT_WRITABLE` now means even root can't write.
  - **gunicorn settings** live in `app/gunicorn.conf.py`, so unknown settings are ignored by older versions. `control_socket_disable = True`: gunicorn 25.1+ otherwise tries to make `~/.gunicorn/gunicorn.ctl` on the read-only filesystem.
  - **Updater:**
    - removes the `docker-compose.override.yml` that 1.12.0 (or Claude) wrote, recognised by its first line; a person's own override is kept.
    - On a busy port (`Start-App`): first tells the person to close Plant record tabs, then retries after 5, 10, 15 and 30 s. Then it moves the port (`PLANTDB_PORT` 8090–8099, `PLANTDB_SENSOR_PORT` 8180–8189, in `.env`).
    - `setup-remote-access.ps1` reads `PLANTDB_PORT`.
  - **Setup script:** `tools/setup-remote-access.ps1` reads `tailscale status --json` in the `plant-tailscale` container (AuthURL, CertDomains, Self.DNSName, User) and makes the signed-in login the owner via `PUT /api/people` on localhost. `tailscale/state` and `.env` are never in a release.

## Sites (decided November 7, 2026; built in `PLAN.md` step 4)
- The app is **one app with many sites**, not one copy per site that syncs. A site is a `locations` row (name, latitude, longitude, time zone; weather is already kept per `loc_id`) grown into the unit that plants, people, weather, frost and seasons hang off. Until step 4 ships, everything is site 1 (Ethan's house) and plants carry no site column.
- When sites arrive: `plants.site_id` (backfilled to 1 in place by `init_db()`), roles per site with the owner over all of them, a current-site helper that every per-site page reads, a units default per site with a per-person override, and a grow-season kind per site (temperate with a winter, tropical wet and dry, no cold season) that decides whether Coming inside, Back outside and the cold-night checklist exist there.
- **Built in 1.48.0 (step 4b), on the homes model that already existed (1.28.0: `locations.plants_here`, `plants.home_id`, the X-Place header and `location(c)`, `plants_at()`):** `locations.country`, `locations.units` (a UNIT_REGIONS key, '' = US) and `locations.season` (SEASONS: temperate, mild, tropical), set through `PUT /api/places/<id>` (`site_fields()` in weather.py; the search result's `country_code` fills the country) and shown on Homes and places (`siteCells()`, act `placesite`). `units_for()` falls back to the place in use's units; `unitsGet()` on the page does the same from `META.place.units`. Season gating: `COLD_PAGES` and `secPages()` in core.js leave Winter plan, Cold-night checklist, Coming inside and Back outside out of the top bar at a tropical home, section links point at the first page that applies, Today leaves out the cold blocks (`winter` in viewToday; registered blocks marked `cold: true`), and the frost banner stays off. Today's feed, Needed from you and requests filter by `atPlace()` (gallery.js) and the health walk-through by `plants_at()`. `people.edit_homes` (JSON list, '' = all) limits an editor: `home_refusal()` in core.py refuses a change whose plant (from the path `/api/plants/<code>`, a care-log id, or the body's plant/plants/plant_code/codes) lives at another home; `me_dict()` tells the page; the people list has a tick box per home for editors (`data-f="pedithome"`). Check: `dev/test/sites_check.py`. **1.58.0 (November 12 review, item 4): the home limit holds on every route.** `home_refusal()` reads the plant out of the request before the route runs (its code in the path, or the body keys `plant`, `plant_code`, `code`, `plants`, `codes`), which missed every request that names the plant another way: a limited editor could remove another home's photos, fertilizer and mix entries and pest sightings, answer its questions, record what it is potted in, undo a bulk change, change its grow light spot, sort it onto a shelf, and add or move plants to a home outside the limit. Now `home_check(c, plant)` (row, code or id; `home_limit()` gives the allowed homes for a change request by a limited editor, else None, so owners, unlimited editors, reading, batches, background jobs, sensors and the plant-sitter's ticks are untouched) is called where a plant is fetched for a change (`plant_row()`), where it is changed (`apply_changes()`, `bump()`, `set_spot_plants()`), and by the routes that reach a plant's records without those (`care_one`, `request_one`, `mixes_plant`, `mixes_pot_del`, `where_spot_delete`); `home_check_new(c, home_id)` covers a new plant (`create_plant`, `several_create`) and a move to another home (`apply_changes` with `home_id`). `home_refusal()` stays as the early answer. `dev/test/unit/test_home_limit.py` tries 40 requests as an editor limited to another home, and its last test fails for any route that changes data and is neither tried there nor listed as not being about one home's plants (`FREE`), so a new route has to be decided.
- The mirror (1.37.0) stays the read-only copy elsewhere; it is not sync and is not meant to become it. Sync between SQLite copies is the one thing this decision rules out; it is revisited only if a site must work with no connection.
