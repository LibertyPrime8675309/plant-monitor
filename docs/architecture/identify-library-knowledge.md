# Identify, the Library, mushrooms, facts with their sources, the propagation guide

Part of the notes on how Plant record is built. The short map is `docs/ARCHITECTURE.md`; this file holds the detail for one area, moved here word for word on November 15, 2026.

## Notes from the back end and front end lists
- **1.18.0 Identify and the plant library:**
  - **Vision service** (`vision/service.py`, `vision/Dockerfile`, compose service `vision`, container `plant-vision`): Flask + gunicorn (1 worker, 4 threads) on port 8090, on the compose network only (no `ports`). Read-only root, `cap_drop: ALL`. Mounts `./data:/data:ro` and `./data/vision:/cache`. Env: `VISION_MODEL` (from `PLANTDB_VISION_MODEL`, default `bioclip-2.5-vith14`, or `bioclip-2`) and `PLANTDB_VISION=0` (answers `state: off`, loads nothing).
    - On start, `load_all()` runs in a thread and reports progress in `S` (`/status`). It loads the open_clip model from `hf-hub:imageomics/<model>`, with weights memory-mapped from safetensors.
    - `fetch_names()` downloads the Plantae block of the TreeOfLife-200M text embeddings (`txt_emb_<model>.json` and `.npy`, CC0). It fetches one HTTP Range request per embedding dimension, because the `.npy` is stored D x N, and saves `names.json` plus `names.npy` (float16, unit rows).
    - `fetch_usda()` reads the 52 USDA PLANTS state CSVs (HF mirror `Solshine/USDA_Plants_Database_By_State_WorkingGroupList`) into `usda_states.json`.
    - Scopes are masks over the species rows: `world`, `us`, `texas`, `common` (has a common name, or is in the US).
    - `index_photos()` embeds every active plant's photos into `photos-<model>.npz` (saved every 25 photos). `watch_photos()` re-checks every minute when `plants.db` changes.
    - `POST /identify`: the best photo per plant (top 5). The first gets `confidence` from `CONF[model]`, a logistic fit on Ethan's photos of margin to the second plant and score. `likely_new` is set when the best score is under `NOVEL[model]`. It returns species top 5 (softmax over the top 50 of the scope) and `genera` (summed). `GET /names?q=&scope=` does a substring search over scientific, BioCLIP common and USDA common names.
    - The tests behind the numbers are in `dev/vision/` (see its README).
  - **App routes** (`server.py`, block "1.18.0"):
    - `POST /api/identify?scope=` (`VIEWER_POSTS`: allowed for viewers, since it changes nothing) forwards to `PLANTDB_VISION_URL` (default `http://vision:8090`). It adds plant names and photos (`plant_brief()`) and `yours` / `yours_genus` (`mark_owned()`).
    - `GET /api/identify/status`, `GET /api/library`.
    - `GET/PUT /api/identify/settings` (PUT in `OWNER_ONLY_CHANGES`) keeps `plantnet_key` and `claude_key` in `settings`. Only `key_hint()` (the last 4 characters) is ever returned or audited.
    - `POST /api/identify/plantnet` (Pl@ntNet v2 `identify/all`, organs auto) and `POST /api/identify/claude` (Messages API, model `CLAUDE_MODEL`, asks for JSON). Their URLs can be overridden with `PLANTDB_PLANTNET_URL` and `PLANTDB_CLAUDE_URL` (the tests use these).
    - Errors 502 and 503 come back as JSON. `Permissions-Policy` allows `camera=(self)`.
  - **Front end** (`app.js`, block "1.18.0"):
    - `viewIdentify()` (`#/identify`), with state in `ID`. Camera through `getUserMedia` (rear camera). `idTick()` sends an 800 px frame about every 0.9 s, one at a time, paused while a dialog is open or the tab is hidden. It also reads label QR codes with `BarcodeDetector` when the browser has it.
    - `idLive()` shows the popup when the same plant is first twice in a row at 80% or more. `idPopup()` has three cases: sure (75% or more), "Which one is it?" (45% or more and not `likely_new`), and "Probably not one of your plants".
    - `idPaint()` draws the results. `idAskOutside()` asks for second opinions. `idAddPic()` posts to `/api/plants/<code>/photos`.
    - `viewLibrary(qs)` (`#/library?q=&scope=`): `route()` now splits off `?query` into `qs`.
    - `NEWFILL` pre-fills the Add a plant form (and attaches `__pic` after saving). It is cleared on any other route.
    - Change buttons are in the viewer CSS block.
  - **Tests:** `dev/test/mock_vision.py` is a fake service (decides by picture colour, and also fakes Pl@ntNet and Claude), started by `mock_server.py` unless `MOCK_VISION=real`. `dev/test/identify_check.py` uses a fake red camera (`.y4m`).

Masks `plant` / `fung`, scope `fungi`, kinds mushroom / cupfungus / lichen / rust / mould / otherfungus. `/status` has `fungi`, rows have `kingdom`, and `/scope_names?scope=` lists every name in a list.

Routes `/api/fungi`, `/api/fungi/<code>` (PUT needs `base_version`), `/status`, `/photos`, `/api/fungi/photos/<id>`. Audit kind `fungi`. Permissions-Policy allows `geolocation=(self)`.

Progress is kept in memory (`PREFETCH`), so after a restart the button picks up where it stopped.

They are kept in `data/library/local/*.json`, cached in memory by file time (`local_get()`), and refreshed by `know_worker()` through `know_refresh()` (it shares `inat_get()`'s one-a-second pace and the `library_online` switch).
  - `TX_NOXIOUS` holds the TDA list. A key ending in a space is a whole genus.
  - `know_of()` / `know_mark()` (called from `mark_owned()`) add `know` to every species: `tx`, `invasive`, `near`, `bloom`, `fruiting`, `pets`, `hardy`. `/api/library/browse?know=` (`KNOW_FILTERS`) sends name and genus lists to the vision service's `/browse` as a POST body (`only`, `only_genera`).
  - **Care sheets:** `POST /api/library/care` asks Claude (`CARE_ASK`, the owner's key) for JSON and keeps it in `data/library/care/<slug>.json`. Its `zone_low` against `home_zone()` decides "zone-yes" or "zone-no".
  - Routes `/api/library/local` (GET, and POST to refetch) and `/api/library/around`. Front end: `spHomeHtml()`, `spPetsHtml()`, `spCareHtml()`, `viewAround()` (`#/around`), and the `libknow` filter.

- **1.27.0 uses, partners and propagation (species facts):**
  - Tables `species_facts(key, name, kind, data JSON, origin 'researched'|'claude', written_by, written_at)` and `facts_link(code, key)`.
  - `facts_keys(sci)` gives the keys, most exact first ('genus species', then 'genus'; a leading x/× is dropped). `facts_row()` tries `facts_link`, then those keys. `facts_clean()` keeps the expected fields at set lengths, and for a fungus drops any use about eating it (`FACTS_FUNGUS_NO`).

  - Batch keys `species_facts_add` (INSERT OR IGNORE) and `facts_link`. Batch A9 is built by `dev/seed_src/build_batchA9.py` from `facts_A9.py`.
  - Front end: any `.facts-box` (`data-facts-code` or `data-facts-name`, `data-facts-kind`) is filled by `loadFacts()`/`factsHtml()`; `factswrite` is in the viewer CSS block. `facts_check.py` covers it, with a mock Claude answer in `mock_vision.py`.
- **1.27.0 wishlist prices (app/shops.py, no Flask in it):**
  - `DEFAULT_SHOPS` are seeded into `shops` (INSERT OR IGNORE). `kind` is `api` (eBay Browse API with an app token from client credentials; Etsy Open API v3 with `x-api-key`), `page` (lines of the listed pages that name a wishlist entry, with a `$` price on the line), or `auto`. `auto` is worked out by `detect()`: Shopify `/products.json`, then WooCommerce `/wp-json/wc/store/v1/products`, then page, and the result is kept in `shops.platform`.
  - `terms_for()` gives a wishlist entry's searches (its `search_words`, else its common and scientific names). `matches()` needs every word of one search in the title.
  - server.py: `shop_fetch()` waits `SHOP_GAP` seconds per host and sends `SHOP_UA`. `shops_worker()` (thread, `SHOPQ`) reads each enabled shop once per check, then `offers_save()` (`offers`, `offer_history`) and `wish_alerts_make()`, which makes one `wish_alerts` row per entry per check; `wish_alert_marks` stops repeats. `shops_loop()` runs it every `shops_hours` (setting, default 12; `PLANTDB_SHOPS=0` turns the loop off).
  - Wishlist columns `max_price`, `alert_stock`, `search_words` (added by `init_db()`). Routes: `/api/shops` (changes owner-only, in `OWNER_ONLY_CHANGES`, which also covers `/api/shops/keys`), `/api/wishlist/check`, `/api/wishlist/offers`, `/api/wishlist/alerts`.

## Identify in two modes (1.51.0, PLAN.md step 5b)
- `vision/service.py`: `/identify?mode=mine|new&country=CC`. `MODES` says which lifts each mode may use: `mine` = own_sp, own_gen, house, state, looks (as 1.39.0); `new` = state and `country`. `prior_why(i, scope, mode, C)` and `prior_bonus()`; the country lift is `PRIOR['country']` (1.0) times a weight that grows with the species' occurrence count (`log10(n+1)/3`, capped at 1). `country(cc)` returns the entry for a two-letter code: loaded from `gbif-<CC>.json` in the cache, or `{'state': 'fetching'}` while a background thread runs `gbif_country.fetch_country()` (GBIF occurrence search, `kingdomKey=6`, `facet=scientificName`, 5,000 names a page, `facetMincount=3`, names cut to genus and species); `error` when it failed. The answer carries `mode` and `country: {code, state, species}`; `/status?country=CC` says the list's state. `vision/gbif_country.py` is copied into the image beside `service.py` and can be run by hand.
- `identify.py` (library.py before 1.57.0): `ID_MODES`, `id_mode()` (`?mode=` on every identifying route, 'mine' when missing), `site_country(c)` (`location(c).country`, 1.48.0), `identify_pictures(..., mode)` adds `mode` and `country` to the service call; `BASIS_WORDS['country']`; `/api/identify/status` carries `site_country` and the service's `country`. `plants.py`'s three identifying routes pass `id_mode()`.
- Front end (`identify.js`; `discover.js` before 1.57.0): `ID.mode`, `idModePref()` (localStorage `plantdb.idmode = {identify, add, plant: 'ask'|'mine'|'new', last}`, in `prefs.js` KEYS so it syncs), `idModeFor(page)`, `idPickMode(page)` (the rule, or a hand choice on the Identify page this visit, or the question: a modal with two `.idm-btn` buttons, the last answer first, and a "do not ask again" box), `idModeNote(r)` under results. `idAsk()` sends `mode`; `plantIdentify()` asks once per plant (`PLANTID.mode`); `sevGo()` asks once per batch (`SEV.mode`); the Add a plant form asks once per form (`NEWID.mode`, events.js `newfill`). The Identify page's two selects are `data-act="idmode"` and `data-act="idscope"` (changeActs; the scope select had no handler before 1.51.0, so its choice was never saved). Display: the Identify part (`ui.js`, act `idmodeset`). Styles: `static/css/identify-modes.css`. Tests: `dev/test/unit/test_vision_prior.py` (modes, country weights, `canon()`), `dev/test/idmodes_check.py`; `dev/vision/prior_test.py` has a "new find" row.

## Knowledge with provenance (1.53.0, PLAN.md step 6a)
- `app/plantdb/facts.py`: table `facts(id, key, kind, field, value, source, source_kind, noted_by, noted_at, confidence, status, replaces, note)` (`KNOWLEDGE_SCHEMA`, run by `init_db()`; `FACTS_SCHEMA` was already the 1.27.0 blob's). `key` is `facts_keys()[0]` (binomial, else genus). `FACT_FIELDS` = (field, kind, label, group): species-level plant columns, `about_*` (the species_facts sections), `sheet_*` (a care sheet's sections); `PLANT_FACT_FIELDS` are the ones that are plant columns too. `fact_value_text()` normalises a value for storage and comparison (numbers as `6` not `6.0`, lists and dicts as JSON); `fact_value_out()` reverses it. `fact_add()` writes a row and retires the field's previous accepted row (`replaces`), skipping an identical value. `facts_of(c, sci, code)` gives the accepted row per field, the most exact key first (a plant's `facts_link` key before its name's keys).
- `facts_migrate(c)` runs at the end of `init_db()` once (setting `facts_loaded`): species_facts → about_* rows (source Claude, researched or asked); `data/library/care/*.json` → sheet_* rows; for each binomial key among active plants, every `PLANT_FACT_FIELDS` value the species' plants agree on → one row, with `value_source()` replaying `batch_sources()` (seed.json, then each batch's `plants` (matched by the plant's names, since codes are given at apply time) and `updates.set[field][1]`) to name the batch or list that set it; untraced values by a Claude author read "an upgrade batch, which one could not be traced"; others "Edited in the app on <code> by <who>" (observation). `facts_from_batch()` handles a batch's `facts_add` (called from `apply_batches`).
- `species_fill(c, p)`: fills empty `PLANT_FACT_FIELDS` on a plant dict from the species' accepted facts and sets `p['from_species'] = {field: {source, confidence, label}}`; `GET /api/plants/<code>?fill=1` (the plant page, `plant.js`); the edit form asks without it. Routes: `GET /api/facts/rows?name=|code=` (groups → fields → accepted + history), `GET /api/facts/export` (JSON) and `/api/facts/export.csv`.
- 6b (1.54.0): `STATUS` gains `rejected`. `POST /api/facts/rows` → a proposed row (`fact_key_for()`: name, a plant's facts_link key, or a key; a source is required; int/num checked; a `kind: fungus` proposal may only use about_*, sheet_*, native_range, danger_*, conservation_status, invasive, and `FACTS_FUNGUS_NO` refuses edible-talk). `POST /api/facts/rows/<id>/accept` (owner, or an editor who is not the proposer; retires the field's accepted row and sets `replaces`), `/reject` (reason appended to `note`), `GET /api/facts/queue` (with `current`, the species' or else the genus's accepted value, and `can_accept`), `POST /api/facts/import` (export JSON → proposed rows, duplicates skipped). Audit rows have action `fact`. `me_role()` reads `g.user`.
- Front end `js/facts.js` (one `addFeature()`): the species page section `#sp-facts-rows` (anchored beside the "Uses, partners" section; groups as `<details>`, Temperature and Light open), and the plant page line `#fr-plant` before `#temp`; 6b adds acts `frpropose`, `fradd` (the form, `frPropose()`), `fraccept`, `frreject` (`frReview()`), the page `facts` ("Facts to review", `viewFactsQueue()`, in the Plants section after Year in review) and the Today block `today-facts` (order 72, editors only); `FR_CUR` holds the species page's rows for the form. Viewer CSS block hides the four buttons. Styles `css/facts.css`. Tests: `dev/test/unit/test_facts_rows.py`, `dev/test/factrows_check.py`, `dev/test/factreview_check.py`.

## The identification loop (1.52.0, PLAN.md step 5c)
- `core.py` SCHEMA: `id_examples(kind 'yes'|'no', name, file, source, plant_code, added_by, added_at)`. `identify.py` (library.py before 1.57.0): `example_picture()` saves the sent picture as `ex_<hex>.jpg` in `PHOTO_DIR`; `POST /api/identify/confirm` (form: name, source, image, or plant for the plant's main photo; viewers refused since it is not in `VIEWER_POSTS`) writes a 'yes' row and an audit entry; `POST /api/identify/reject` also takes a form with `image` (a 'no' row for a species, not a genus; with `plant` and no picture, the plant's main photo); `GET /api/identify/examples` counts by name. `BASIS_WORDS['unlike']`.
- `vision/service.py`: `EXAMPLES`, `examples_rows()` (id_examples plus the photos of active mushroom finds named at least "Fairly sure"), `index_examples()` (fingerprints in `examples-<MODEL>.npz`; run after `index_photos()`, so the 60-second watcher picks new rows up). In `/identify`, the look-alike step searches the examples in both modes: a 'yes' within `NOVEL` similarity lifts like a record photo (`looks`), a 'no' lowers by the same scaled amount (`unlike`). `/status` carries `examples: {yes, no}`.
- Front end (`identify.js`; `discover.js` before 1.57.0): `idConfirm()` (act `idright` on Identify result cards with the shot, and on the plant page with the plant code), `idReject()` sends the picture with "Not this" when there is one; `spCard()` shows "This is right" for `reject` contexts `id` and `plant`, editors and the owner only (viewer CSS block too); `idStatusText()` says what it has learned. Checks: `test_vision_prior.py`, `test_server_pure.py`, `dev/test/idloop_check.py`.

## Propagation and breeding guide (1.57.0)
- **Words on the front end, one list on the server.** `static/js/guide.js` holds the guide's text as data (`GD_GOALS`, `GD_RULES`, `GD_METHODS`, `GD_BREEDING`, `GD_MOTHER`), so the page works offline like any page. Lengths are written `[[2 to 4 in]]` and shown by `gdText()` in the person's unit (`lenF`); temperatures are written in °F and `linkify()` converts them. A new method is one more object in `GD_METHODS` (its `id` starts `gd-`, which is also the `?sec=` it can be opened at) and one more pattern in `gdKeys()` if free text should map to it.
- **Matching your plants.** `plantdb/guide.py` (ORDER 60) has one read-only route, `GET /api/guide/plants`: for each active plant with any note, its `plants.propagation` lines, then its species' methods from `species_facts` (`facts_row()`; a fungus's facts are left out). `gdKeys(line)` turns a line into the sections it is about: each pattern's match is taken out before the next is tried, so "air layering" is not also "layering" and "leaf cuttings" are not also "cuttings". `gdMatch()` builds `{section id: [{code, name}]}`; `gdYours()` writes the line under each method (left out when the server cannot be reached). The mapping lives in one place (the browser); the server sends the words.
- **Registered, not wired in.** One `addFeature()`: the page `#/guide` (`nav: 'library'`, a label so Search finds it, no top-bar link) and three adds with ids `gd-plantlink` (plant page `#uses`), `gd-specieslink` (species page facts section) and `gd-liblink` (the Library's button row). The one edit outside the module is `guideLink(method)` in plant.js's `factsHtml()`, which puts **How to** beside each method of a plant's or a species' facts (not for a fungus).
- A method's group is `details.grp.gd-method` with its `id`; `viewGuide()` opens the one `?sec=` names, and the router's `?sec=` handling scrolls to it. Nothing on the page changes data, so no viewer rule or `OWNER_ONLY` entry is needed.
- **Tests:** `dev/test/unit/test_guide.py` (the lines for a plant, the route); `dev/test/guide_check.py` (the page, the lists, which words mean which section, deep links, metric units, links from the plant page, Library and Search, phone width with the largest text in dark mode).
