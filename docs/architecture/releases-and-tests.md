# Releases, and how old records and built images are tested

Part of the notes on how Plant record is built. The short map is `docs/ARCHITECTURE.md`; this file holds the detail for one area, moved here word for word on November 15, 2026.

## The release rhythm (1.55.0, PLAN.md step 7)
- **Releases are made by GitHub.** `.github/workflows/release.yml` runs on a push to main that changes `VERSION` (and by hand): if no release `v<VERSION>` exists it waits for the Images workflow on the same commit (so the images the updater pulls exist before the release does), runs `tools/make-release.py`, and `gh release create`s "Plant record <version>" with `dist/plant-database-v*.zip`, every `dist/plant-database-photos-*.zip` (packs are rebuilt from `app/seed/photos` each time and never change, so attaching them all is safe and lets the updater fetch any it lacks) and the CHANGELOG entry as notes. `permissions: contents: write`. Saving a zip into Ethan's folder from a chat is the fallback, not the way.
- **The updater** (`tools/update-plant-database.ps1`, step 0): `Invoke-RestMethod` on `repos/<Repo>/releases/latest`; when the tag is newer than the newest `plant-database-v*.zip` in `versions_plant-database`, `Download-Asset` fetches the zip asset (to `.part`, then moved); the photo-pack step downloads absent packs from the same release before deciding they are missing. `-NoDownload` skips GitHub, `-Repo` points elsewhere; a failed fetch is a yellow line, not a stop. The Dockerfile copies `CHANGELOG.md` into `/app` so the container can read it.
- `app/plantdb/releases.py`: `changelog_entry(version)` parses `## x.y.z (date)` blocks of `CHANGELOG.md` (`/app/CHANGELOG.md` in the container, the repo root in the mock) into `{version, date, lines}` (bullets without their dash, inner headings dropped, 12 lines at most; the top entry stands in when the running version has none). `check_latest()` GETs `api.github.com/repos/<REPO>/releases/latest` and keeps `settings.latest_release` = `{version, url, published, checked, assets}` (`latest_release_failed` on a miss, the old value kept); `updates_loop()` runs it 90 s after start and every 12 h (`PLANTDB_UPDATES=0` or the mirror: off; the mock and unit tests turn it off). `GET /api/whatsnew` → `{version, entry, seen, update, restore}`: `seen` is the pref `seen_version` of `prefs_login()` (per person, the local owner shares the Tailscale owner's); `update` only for the owner and only when `newer(latest, APP_VERSION)`; `restore` (owner) = `{last, days, due}` from `settings.restore_tested_at`, which `backups.restore_backup()` writes (1.55.0) — `RESTORE_DAYS` = 90. `POST /api/whatsnew/seen` is in `VIEWER_POSTS` and allowed on the mirror, like `/api/me/prefs`. `GET /api/whatsnew/all` renders the whole CHANGELOG as a plain HTML page (escaped; `**bold**` only).
- `js/releases.js` registers three Today blocks: `rl-new` (order 2, `.notice`, "Got it" = act `rlseen`, link to `/api/whatsnew/all`), `rl-update` (order 3, owner), `rl-restore` (order 85, section `#rl-restore`). One `/api/whatsnew` request serves all three per Today draw (`rlLoad()`, 5 s). Checks: `dev/test/unit/test_releases.py`, `dev/test/releases_check.py` (the update line is tested by changing the API answer on the way to the page, since the mock never asks GitHub).

## Old records and built images are tested (1.58.0; November 12 review, item 6)
- **Why.** Every check started from a new install and ran the source on Flask's own server. Ethan's record has come through every version since October, and what his PC runs is the built image. The failures that reached him were of those two kinds.
- **Old records:** `dev/test/unit/test_upgrade.py` (about 8 seconds, part of the unit tests). `dev/test/fixtures/plants-<version>.sql.gz` is the database a version leaves behind after ordinary use, as SQL text: 1.7.5 (the first commit), 1.28.0 (the last before rooms and spots and before the `plantdb` package) and **the last release** (the upgrade his own record makes next). `dev/test/fixtures/make_upgrade_fixture.py <old app folder> <out>` makes one: it starts that version on an empty folder and, through its own routes, edits two plants, adds a plant with a photo, logs a feeding and a watering, answers a question, archives a plant, moves one indoors, and where the version can makes a group, a shelf with a plant on it, a grow light spot, a pot's mix with a repot, a plant-sitter link, and turns the photos off in automatic backups. **After each release, make that release's fixture and remove the one before it** (`git archive <release commit> app | tar -x -C /tmp/old`, then the script; the constants at the top of the script and of the test must stay in step).
  - The test loads each fixture into an empty data folder and starts this version on it in a process of its own (`python -c "import server"`, as a container start does), then starts it again. It asserts: integrity and foreign keys; `db_version`; every batch marked once and old marks untouched; no "could not find" line; every row a person made is still there (`KEPT`: care log, feedings, questions and answers, groups, shelves, plants on shelves, light spots, potting mixes, sitter links, photos, page versions, the audit log); the hand edits read as written; a saved `photos: false` is switched once; **the upgraded record equals a new install of this version** (same tables, columns and indexes; the lists batches bring; every plant matched by its name and photos, with the same facts and photos, except `BY_HAND`; every active plant in an area of its own home whose kind matches its `site`; the owner's plant the only extra); a second start changes nothing; 24 pages answer; and a batch written the new way (code plus name) lands on the right plants while one that sets a row number is refused.
  - Its first run found the two batch defects described under "Which plant an entry means" above and in `BATCH_ROW_IDS` (batch C9 carried `area_id: 7`, copied from another plant's row by `build_batchC9.py`: the Baraboo orchid sat in a room of the main home, a different room in every record). Neither had reached Ethan's PC: his record has no plant of his own, and C9 is not released.
  - A difference the test allows: in the 1.7.5 fixture the person moved a plant indoors before any room existed, so the stand-in "Living room" (`where_seed()`) kept that plant and is the first indoor room; plants a later batch adds indoors go there, not to "Downstairs Living Room". Areas are therefore compared by home and kind, not by name.
- **Built images:** `dev/test/image_check.sh <image name> <version> [image]`, run by `images.yml` after the build and **before** the push (so an image that does not start is never published). App image: copies `docker-compose.yml` into an empty folder with an override (that image, `pull_policy: never`, weather, stores, updates and notifications off), `docker compose up -d --no-build plants`, waits for `/healthz`, checks `/api/meta` (version, plants from the seed), the page and its files, `/api/health` (which user it runs as, the saving mode), that a foreign `Host` gets 403, makes a backup the way the updater does (`POST /api/backups {wait, kind: update}`) and finds the zip and `data/plants.db` on the host, restarts the container on that data and counts the plants again, and fails on a problem of the app's own (areas backup, database, batch, start) on the Problems list. Speech image: decodes one second of sound with faster-whisper, PyAV and CTranslate2 and imports `service` with `PLANTDB_SPEECH=0`. Vision image: imports torch, open_clip and the rest and `service` with `PLANTDB_VISION=0`. No model is downloaded and nothing needs the internet.
- **Waiting in browser checks:** `dev/test/waits.py` has `until(pg, fn)` (asks until true, 15 s at most) and `redrawn(pg, selector)` (call before an action; what it returns waits until that element has been replaced). The checks hold about 1,100 fixed pauses; on November 12 `pots` failed on GitHub because a save outlasted its 1.5 s pause. `pots_check.py` uses the new waits throughout. Convert a check when you change it; a pause that has nothing to wait for can stay.
