# Records, upgrade batches, weather, backups and update files

Part of the notes on how Plant record is built. The short map is `docs/ARCHITECTURE.md`; this file holds the detail for one area, moved here word for word on November 15, 2026.

## Notes
- **Upgrade batches** (`seed/batches/*.json`) are applied once each, in filename order, and recorded as `settings` key `batch_applied:<id>`. Keys:
  - `plants`: new pages, numbered next free `P-###`. Each can carry `photos` and `take_photos` (`[{file, from, name}]`, which moves an existing photo onto the new page). A new page cannot carry `home_id`, `area_id`, `spot_id`, `pot_id` or `tray_id` (`BATCH_ROW_IDS`, dropped when read): `home_near: {lat, lon}` says the home, and `where_seed()` gives the page the area of that home that matches its `site`.
  - `existing_photos`: `[{code, name, photos, file, caption, primary}]`
  - `updates`: `[{code, name, photos, note, set: {field: [old, new]}}]`. A field is only changed if it still holds `old`; otherwise a note is logged. A row number (`BATCH_ROW_IDS`) cannot be set: the start-up fails, so such a batch never passes a check.
  - `archive`: `[{code, name, photos, note}]`
  - `requests_add`: `[{key, code, name, photos, kind, text}]`
  - `pot_mixes_add`: `[{code, name, photos, mixed_on, parts, top, bottom, notes}]`; `facts_link`: `{code: key}` in the old files, `[{code, name, photos, key}]` from now on.
  - **Which plant an entry means (1.58.0).** Every entry above goes through `find_plant(c, entry, meant)`: by `photos` first (files on its page, the most stable clue); otherwise by `code`, and the plant must carry `name` when one is given. **A code in a batch file is the code a new install gives the plant**, not necessarily the code it has in this record: `batch_numbering(c)` returns `meant = {file code: plant id}` (the first list's own codes, then each batch's new pages in order, read from the log line `CREATED_BY_BATCH` each one left; a batch whose log does not have as many pages as its file is left out, so its codes mean what they say) and `apply_batches()` adds each page it makes. In a record with no plants of the owner's own (Ethan's, November 2026) the two are the same. In one where the owner added a plant before a batch made its pages, those pages have the next codes, and an entry that named one by its code alone (136 photos, 7 potting mixes, 10 updates and a facts link in the files up to D1) used to land on the neighbouring plant. A plant the owner added is not in `meant`; an entry reaches it by the code it has in his record **plus its name**. So from the file after `batchD1.json`, every entry that names a plant by its code also gives `name` or `photos` (`dev/test/unit/test_batches.py`), and an entry whose plant cannot be found is left out with a line in the Audit log.
  - `requests_done`: `[key or {key, answer}]`
  - `to_photograph_add` / `to_photograph_done`
- **Weather:**
  - Data comes from Open-Meteo: forecast, archive and geocoding, with no account needed.
  - A background loop updates every enabled place hourly. "Load history" backfills years of readings in chunks, with retries and progress shown in `/api/weather/job`.
  - Recent years keep full hourly detail; older years keep core hourly values plus daily summaries.
  - `/api/readings/series` aggregates readings for the charts.
- **Backups:** `make_backup()` uses SQLite's backup API to write a zip containing `plants.db`, `backup.json` and optionally the photos. `backup_loop` handles automatic backups. `POST /api/backups {wait:true, kind:'update'}` is what the updater calls. **1.58.0 (November 12 review, item 2):** `BK_DEFAULTS['photos']` is True, and `backup_photos_once()` (called by `init_db()`, marker `backup_photos_once`) switches a saved `photos: false` to true once unless `photo_bytes()` is over `PHOTOS_ONCE_MAX` (1 GB), with an audit row signed "Plant record"; a later untick is kept. `prune_backups(keep)` also removes `update` backups beyond `KEEP_UPDATES` (5); it runs after automatic and before-update backups (the updater's `wait` request too). Manual ones are never removed. `backup_notes(c)` lists what the owner should know, as keys: `off`, `photos` (with the photo count, bytes and the newest backup that has them), `one-drive` (`copy_away(c)` in copies.py is false: no `PLANTDB_COPY_DIR` named and no receiver; docker-compose now passes `PLANTDB_COPY_DIR` into the container, which the app could not see before, so `dir_env` was always empty). They ride in `/api/backups` (`notes`, `keep_updates`), `/api/health` (`backup_notes`, `copy.away`) and `/api/jobs` (`backup_notes`, keys only); `bkNote()` and `bkNotesHtml()` in ui.js put the words to them (Backups page top with acts `bkphotoson` / `bkautoon`, the Health card, Today's quiet line for the owner). The mock server maps a second-copy folder beside its data, as an installed copy has. Not done: leaving the weather readings out of the zip (nearly all of a large database, and they download again).
- **Update files from Claude (1.58.0, review item 12; `plantdb/updates.py`, `js/updates.js`, `css/updates.css`):** corrections, photos and new pages for Ethan's own plants arrive as a file, not in an upgrade batch, so his plants' details stay out of the public code and need no release. The format (`plant-updates-1`) is at the top of `updates.py`: `changes` of kind `set` (`code`, `name`, `field`, `from`, `to`, `why`), `archive`, `ask` (`text`), `photos` (pictures for a page that exists) and `new` (`fields`, `photos`, and `home`: the name of the home it is at, never a row number; none means the main home); a `.zip` holds `updates.json` and `photos/<name>`. `upd_parse()` reads a file as data and refuses anything else in plain words (`ValueError`); a file's id is the first 16 hex digits of its SHA-256, so the same file is the same update under any name. `upd_files()` lists Claude's folder (`UPD_FOLDER`: `/plant-updates`, which docker-compose mounts read-only from `./plant-updates`; `PLANTDB_PLANT_UPDATES_DIR` names another) and the page's own (`data/plant-updates`, where an upload is kept as `<id>__<name>` until it is used). `upd_review()` weighs each change against the record as it is now: `ready`, `conflict` (the page no longer holds `from`, or a new page's name is taken: the owner decides), `same`, `out` (plant not found by code and name, a field a file may not set, a value `norm()` refuses, a photo that cannot be read, a home the record does not have: `upd_home()`). Photos are saved by `upd_save_photos()` the way Add photos saves them (written again, so nothing of the camera or the place stays in them; the page's main picture stays), with one `photo_add` version for the page. `POST /api/updates/<id>/apply {accept, take}` reviews again, makes the accepted changes in one transaction through `apply_changes()` and `bump()` (signed `Claude (<file>)`, note: the reason and who accepted), writes the row in `update_files` (`state` `done` or `aside`, `result` JSON) and removes the page's copy; on any failure nothing is kept, the photos already written included. `GET /api/updates` (waiting, before), `POST /api/updates/upload`, `GET /api/updates/<id>`, `GET /api/updates/<id>/photo/<name>` (a smaller copy, for the review), `POST /api/updates/<id>/aside {on}`. All of `/api/updates` is in `OWNER_ONLY_PATHS`. The page is `#/updates` and `#/updates/<id>`; Today's line is a registered block (`upd-today`, order 6) that asks only for the owner. `tools/check-plant-updates.py FILE` checks a file before it is saved. (`PLANTDB_UPDATES` is unrelated: it turns the check for a newer release on or off.)
- **Weather backup (1.58.0, `plantdb/wxbackup.py`):** the weather history (`readings` with `source='weather'`, `weather_daily` except forecasts) is backed up apart from the rest, as immutable pieces in `backups/weather/` (`plantdb-weather-<stamp>-full|part.zip`: `weather.db` plus `piece.json` with a checksum per place and day). `wx_make()` compares every day's checksum (`wx_scan()`) with what the pieces hold (`wx_have()`, a later piece's day wins) and writes the whole of each new or changed day; `wx_combine()` writes one full piece and removes the old ones only when its checksums equal theirs; `wx_fill()` adds what the record lacks (`INSERT OR IGNORE`, places matched by device, else position). `make_backup()` leaves the weather out when `wx_covered()` (the weather backup is on and a readable piece exists) and writes `weather: false` in `backup.json`; `restore_backup()` then copies the record's weather into the backup's database before it takes its place (`wx_carry()`), or fills from the pieces when there is none. `backup_loop()` calls `wx_backup_tick()`; the schedule is the setting `wx_backup`. Piece names always sort in the order they were made (`_wx_name()`). Tests: `test_wxbackup.py`, `wxbackup_check.py`. Not done: pieces are not sent to the receiver, so a mirror has no weather history.
